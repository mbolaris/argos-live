# Shared foundations and owner-approved improvement

Agreed product direction, October 8, 2026. This is a roadmap, not a claim that
these capabilities or autonomous experiments are implemented.

## Purpose

Build a private personal AI that evaluates its demonstrated performance, proposes
useful improvements, and carries out approved, bounded experiments to serve its
owner better. Improvements concern the whole assistant system: model choice,
task instructions, Ollama configuration, hardware use, tools and reviewed skills.
This is system improvement, not weight training or evidence of recursive AGI.

Do not ask a new owner to design a curriculum or choose a profession. The early
skill ladder and map are shared by every installation. Lead with one recommended
next mission and one Start action. Let the owner watch real work, understand the
result and approve a concrete next experiment. Alternatives belong in Details.

The owner's shorthand is getting the AI through "K–12" before specialization.
Use it as a progression metaphor, not literal school-grade equivalence, a child
persona, an IQ score, or a promise that completing the map produces AGI. No fixed
number of grades or curriculum pass thresholds is established by this document.

## Shared foundation ladder

| Foundation | Demonstration | Scope limit |
|---|---|---|
| Follow directions | Follow constraints and produce the requested response format | Valid JSON alone does not prove planning or tool use |
| Read carefully | Extract facts, quote supporting evidence, distinguish missing information | Short-document qualification does not prove long-document or file access |
| Work with numbers | Calculate, handle units and check a result | Format failures and incorrect calculations remain separate |
| Reason and plan | Order steps, account for dependencies and revise a flawed plan | A written plan does not prove successful execution |
| Use tools | Operate permitted tools in a controlled sandbox and verify artifacts | Requires actual execution evidence under J4, not simulated tool-call text |
| Complete a mission | Combine demonstrated foundations on a useful task and verify its outcome | Owner acceptance and fixed test qualification are distinct evidence |

These are curriculum domains, not six implemented levels or mandatory model-size
upgrades. Existing coverage remains available. The first focused experience is
**Read this brief**, using the existing eight passages, 24 scored questions and
eight unscored owner-judged summaries. Following directions is also exercised
there; it is not a new prerequisite blocking this first mission.

Add later rungs only with versioned original tasks, explicit criteria, suitable
budgets and truthful evidence. No tool rung becomes runnable before its sandbox
exists. Label future areas as not available, rather than inviting impossible tests.

## The visible loop

**Next mission → watch → understand → approve one experiment → retest
→ keep or restore → try useful work.**

The map supplies context; it is not the primary navigation burden. Show
demonstrated, needs work, not tested and unavailable distinctly, with scope and
the configuration/model identity supporting each state. Partial or cancelled
runs cannot qualify. Repetition, downloading a larger model or spending money
does not by itself earn progress. Historical evidence stays visible without
being inherited by a new model or recipe.

The AI should eventually recommend one experiment grounded in its receipts, for
example: "I added unsupported details. I suggest testing an instruction that
requires evidence for each answer." Its explanation can express personality;
the interface independently shows the facts and controls. Model opinion is not
the scorer, a readiness signal or an executable plan.

Approval shows the exact proposed intervention, hypothesis, matched tests,
resource limits, affected scope and rollback. An owner can approve a bounded
plan containing predefined candidates; execution within that plan should not
require repeated questions. Failed or expired approval does not start work.
No new permissions, model substitutions or unapproved candidates are included.

The experiment runs in a reversible staging slot. Show answers, receipts, elapsed
time and Stop as work happens. Report gains, regressions and resource tradeoffs;
the owner keeps or restores the result. An unchanged or restored build can be a
good outcome. Keep/Restore currently means Lab recipe selection; promotion into
the personal OpenClaw assistant requires its own transaction and real agent test.

## Evidence and control

- The proposing agent cannot change suites, scoring code, thresholds or acceptance
  policy. Treat its output as untrusted input to a narrow validated plan format,
  not arbitrary commands or configuration edits.
- Freeze comparison conditions and change one declared variable. Preserve the
  strict standard comparator; use the separate controlled-experiment contract
  for intentional interventions. Record model digest, recipe identity, runtime,
  hardware, suite and settings. Unknown or mismatched evidence stays unsupported.
- One extra correct answer is an observed difference. Do not call it confirmed
  improvement or "within noise" without suitable repeated measurements. Show
  speed and correctness separately and allow useful tradeoffs.
- Withhold held-out answers and detailed validation feedback from the proposing
  agent. Keep validation separate from tuning; repeated tuning on a held-out set
  makes it no longer held out. Require independent validation and a useful-task
  check before broader improvement claims.
- Direct Ollama trials establish model/recipe behavior, not actual OpenClaw
  memory, tools or conversation reliability. Agent promotion needs agent-path
  evidence. Device inspection, CPU/GPU inference, browser behavior, firmware and
  persistence across reboot remain separate acceptance scopes.
- Set download, disk, time, output and thermal limits before execution. Increasing
  context, thinking or model size is a tradeoff, not automatic progress. Respect
  observed hardware suitability; do not blindly raise budgets to pass tests.
- Task instructions and personal identity are separate. Preserve owner persona,
  credentials and permissions. Personality changes require their own explicit
  preview and approval. Permission expansion is a separate owner action.
- Log reversible changes and evidence privately. Do not export personal content,
  secrets or hidden reasoning into public reports, streams or unencrypted DATA.
  No internal-disk, firmware or security changes follow from an AI suggestion.

## Specialization later

Once shared foundations are demonstrated, offer optional directions such as
writing, software development or real estate, informed by owner interests and
the AI's evidence-based suggestions. Do not force a career choice to begin.
Specialization extends the common map and adds relevant validation; it never
relabels common scores as professional qualification or high-stakes reliability.

The near-term focus remains J5/J6a/J6b/J7's complete document improvement loop.
Agent-generated proposals follow that foundation. Storage/model changes are J3;
actual tools require J4; identity/personality editing remains P8. None of these
dependencies is waived by the curriculum metaphor.
